# T1 redaction training dataset: design

Date: 23 Oct 2026, late evening (London). Status: agreed in chat with Nick, not yet built.
Scope: the input documents and answer keys for Veil's redaction task (T1), and how they are sent through Mubit. It does not cover the answer task (T2), the UI or the eval harness code.
This design supersedes two points of `docs/NIGHT-SHIFT-TEAM-PACK.md`: T1 now returns the rewritten chunk, not a JSON entity list (team pack FR-4, 8.2, 8.3), and the teacher model is `claude-haiku-4-5`, not `gpt-6-luna`.

## 1. Intent and why

Veil hides personal data in documents before a prompt reaches a frontier model. The redaction model (T1) is an adapter that Mubit trains by distillation: it records our calls and learns to copy the teacher model's answers. Until the adapter serves, every T1 call goes to the teacher at Anthropic, so real customer documents cannot be used for bootstrap training. We therefore build input documents whose personal data is fake.

What we create ourselves is only the inputs, plus an answer key per document. The teacher writes the training labels. The key is generated by code (we know every fake value we inserted and where), and it is used to:

- measure the teacher and each adapter version (leak rate, recall and precision per type, over-redaction);
- find chunks the teacher got wrong, which become the corrections shown in the demo (judging criterion 1).

## 2. Mubit constraints this design depends on

- Training data is recorded live calls; the teacher's reply is the label. Our answer key never enters training directly.
- A task is the fingerprint of model, system prompt, tools, tool choice and output format. All five are frozen before bulk sending (`PROMPT_VERSION = 1`). Any change creates a new task and resets the example count. Per-document text never goes into the system prompt.
- The task display name comes from the first words of the system prompt, so it starts with a meaningful phrase.
- One session per document (`metadata`), because Mubit holds out test cases by session.
- First training at 25 kept examples. Not every call is kept; near-duplicates are wasted. There is no retry button; recovery is always new calls.
- Billing (seen in Nick's console, 23 Oct 23:34): starter credit is available with a $25 balance, "about 5,000 runs", covering Anthropic and OpenAI. Do not add an Anthropic provider key: once added, every Anthropic call of the project bills Nick's own account.

## 3. Decisions made by Nick

1. **Teacher:** `claude-haiku-4-5` through `https://api.mubit.ai/anthropic`, on the starter credit. Estimated cost for about 1,200 T1 calls at about 2,000 input and 1,000 output tokens each: about $8 at Anthropic list price ($1 / $5 per million tokens).
2. **Output:** the whole chunk rewritten with placeholders, as plain text (no JSON, no `json_object`).
3. **Placeholders:** `[TYPE_N]`, for example `[PERSON_1]`, `[IBAN_1]`. The same value gets the same number within a chunk; numbering restarts in every chunk.
4. **Entity types:** all 13 from team pack 7.5: PERSON, ADDRESS, POSTCODE, EMAIL, PHONE, BANK_ACCOUNT, SORT_CODE, IBAN, CARD, NI_NUMBER, DOB, ID_DOC, CUSTOM. Kept visible: amounts, ordinary dates, contract terms, public company names (unless clearly a sole trader's name), product names.
5. **CUSTOM** is described in the system prompt in general terms ("identifiers specific to an organisation"), with no format examples, so the teacher misses unusual formats and those misses become real corrections.
6. **Chunk size:** up to about 1,000 tokens, split on paragraph boundaries.
7. **Sources:** real, publicly available documents. Real personal data in them is replaced with fake values; blank templates are filled with fake values. Nick decided against an automatic check for leftover real values; the risk of a missed replacement is accepted.
8. **Financial and insurance documents:** the en-GB part of `gretelai/synthetic_pii_finance_multilingual` (Apache-2.0), because almost no UK financial or insurance documents exist as public text.
9. **Document groups:** contracts, financial, correspondence, insurance.
10. **Hard cases:** the whole list in team pack 9.4 (names that are common words, names only in signatures, possessives and initials, transliterated names, addresses split over lines, partial numbers such as "ending 4821", company names containing a person's name, one person written three ways, over-redaction traps).
11. **Volumes and splits:** as team pack 9.5: training about 100 documents (300 to 500 chunks), fresh batch 60+ documents (about 200 chunks), corrections 30 to 50 chunks, eval 40 to 60 documents (about 150 chunks, never trained on).
12. **Eval is split by source:** sources in eval never appear in train or fresh.
13. **Variations:** each source is filled about 5 times with different fake values, and each fill also varies the text (clause order, formatting, how names and addresses are written).
14. **Deadline:** not a constraint. If v1 trains after 01:00, that is acceptable.

## 5. Calls made by Claude and approved by Nick

- **Eval holdout:** one source per contract subtype (tenancy, employment, NDA) and 2 or 3 correspondence sources go only to eval. Gretel documents are split by document.
- **Chunks without personal data are sent once per source.** In long documents most chunks contain no personal data and would be byte-identical across the 5 fills. Only chunks with personal data are repeated across fills.
- **Gretel labels are validated before use.** A document is dropped if any labelled span does not match the text at its offsets.
- **Downloads** (the Gretel dataset, PDF sources) are asked for separately, with file sizes.
- **Real-party source files are not committed** to the public repo without Nick's explicit OK.

## 6. What the answer key must contain

For every document: document id, source id, group, split, fill number, full text, and every personal value with its type and character offsets. For every chunk: chunk id, document id, its text, and the expected redacted text, produced by code from the offsets using the placeholder rules in section 3. The key is never written by an LLM.

Scoring compares the teacher's (or adapter's) output with the original chunk to recover what was hidden, then compares that with the key. Because placeholder numbers restart in every chunk, any cross-chunk mapping of `[PERSON_1]` to a real person is done in code.

## 7. Non-goals and anti-goals

**Non-goals:** scanned PDFs and OCR; the T2 answer task; the UI; the eval harness code; LLM-generated documents.

**Anti-goals (the dataset fails even if it technically works):**
- a key written or checked by an LLM instead of code;
- eval sources that also appear in training;
- a flood of near-identical calls that Mubit discards;
- a system prompt, model or output format that changes after bulk sending starts.

## 8. Open questions for Mubit

- Is eval traffic with `x-middleware-record: off` acceptable under "every call through Mubit"?
- Which Anthropic models the starter credit serves. The first test call settles it: `400 starter_credit_model` lists the allowed models.
- How Mubit decides that two calls are near-duplicates.
- Which base model the adapter uses.
- How to run a given adapter version on the eval set: can a record-off call be served by the adapter, or is Try models the only way?
- How corrections reach training: console edits on a request, an API, or something else.

## 9. Calls made after the builder check (Nick reviews these in the morning, before bulk sending)

A reviewer read this design as a builder would. Its questions were settled as follows. All of them only affect the prompt and the sending step, which stay unfrozen until Nick approves them, so none blocks building the documents.

1. **No regex pre-pass before T1.** T1 sees the raw chunk and handles all 13 types itself. The team pack's regex layer (FR-3) can still run after T1 in the product, as a safety net. If Nick wants regex first, the chunk builder and the prompt change before bulk sending, not the documents.
2. **Placeholder numbering is per entity, not per string.** All surface forms of one person or thing in a chunk ("Raj Patel", "Mr Patel", "R. Patel") share one number, using `entity_id` from the key. Possessives keep the suffix outside the placeholder (`[PERSON_1]'s`). A postcode inside an address is a separate POSTCODE entity, as in the team pack example. Scoring is by span and type; placeholder numbers are not scored strictly. This replaces the "same value, same number" wording in section 3.
3. **Finding real values in filed sources:** the building agent reads each source and turns every personal value into a typed slot, then runs a regex sweep for leftover structured identifiers. The key itself is still written by code from the slot fills. The slotted templates are committed so Nick can review them. A real value that was missed stays unlabelled; the scorer lists over-redactions that look like personal data for manual review.
4. **Gretel labels:** a mapping table to the 13 types is committed with the data. Labels for things we keep visible (company names, ordinary dates, amounts, SWIFT/BIC) are dropped. Customer, account and user identifiers, usernames and IP addresses map to CUSTOM. Documents containing passwords or API keys are dropped. A regex sweep looks for unlabelled structured identifiers; a document is fixed if the fix is unambiguous, otherwise dropped.
5. **Corrections:** the correction mechanism is still unknown (section 8). The data supports both known options: unusual CUSTOM formats repeat across train, fresh and eval so the teacher misses some and the fix can show in eval numbers, and the sender stores the `mreq_` id of every call.
6. **Running adapter versions on eval** is an open question for Mubit, added to section 8: `x-middleware-record: off` may also stop the adapter from serving those calls. The sender keeps record-off as a switch.

Nick reviews the wording before bulk sending, because it is frozen afterwards.
- Request settings for Haiku 4.5 (for example `max_tokens` large enough for a 1,000-token chunk), concurrency, and `retry-after` handling.
